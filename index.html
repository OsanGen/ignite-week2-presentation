    COST RECORDS

    What Makes a Cost Record Traceable

    Part 1 of 3

    A traceable record lets someone connect a charge to the course, the run, and the activity or usage that caused it. It also makes the quantity, unit, rate, currency, period, and payer visible, with a source for the calculation.

    TRACEABILITY QUESTIONS

    • Which course and run?
    • Which activity or usage?
    • What quantity and unit?
    • Which rate and currency?
    • Which period and payer?
    • What source supports it?

    Part 2 of 3

    For example, P01 is the whole-run text-input line. It uses three hundred thousand tokens at a fictional rate of two dollars per million tokens. The billing quantity matters: multiplying by two without dividing by one million would apply the rate to the wrong unit.

    SYNTHETIC RECORD | P01

    • Course | SYN-COURSE-001
    • Run | SYN-RUN-001
    • Usage | 300,000 tokens
    • Rate | $2.00 per 1,000,000 tokens
    • Currency | USD
    • Expected cost | $0.60

    Part 3 of 3

    The example does not supply an actual provider contract, a real rate-effective date, or verified payer details. Those fields stay unverified where absent. This record is a way to explain the calculation, not proof that we have DMS's final production schema.

    DO NOT FILL MISSING METADATA BY GUESSING

    • Actual provider and contract | Unverified
    • Actual rate-effective date | Not supplied
    • Actual payer allocation | Unverified
    • Production schema | Not established by this exercise
    • Source | Fixed synthetic example

    DUPLICATES AND RETRIES

    A Duplicate Is Not a New Billable Attempt

    Part 1 of 4

    Submitting the same expense again must not count the same cost twice. In the synthetic duplicate check, capture the ledger before and after resubmitting the same source expense. The expected outcome is no second posting for that same expense, not deletion of the original record.

    PLANNED DUPLICATE CHECK

    • One source expense
    • First accepted posting | One charge
    • Same expense submitted again | No second charge
    • Capture before-and-after ledger evidence
    • Application result | Not tested here

    Part 2 of 4

    Do not decide that two expenses are duplicates just because their amounts match. The identity of the underlying expense matters. If the system's source identifier or retry rules are not documented, that is an open technical question. A retry with an uncertain result needs reconciliation before another posting is attempted.

    EXPENSE IDENTITY MATTERS

    • Same amount ≠ necessarily the same expense
    • Same expense ≠ a new charge
    • Source identifier and retry rules | Must be established
    • Uncertain result | Reconcile before repeating a posting

    TRACEABILITY AND EXPORT

    Make the Export Reproducible

    Part 1 of 3

    An export is useful when another reviewer can connect its amounts to the records and assumptions that produced them. For the synthetic exercise, keep the course and run identifiers, input version, calculation basis, included costs, and known gaps with the exported result.

    PROPOSED REVIEW EVIDENCE

    • Course and run identifiers
    • Input and test-build versions
    • Quantities, units, rates, and rounding basis
    • Included cost rows and totals
    • Missing information and exclusions
    • Exact export format: verify against the test build

    Part 2 of 3

    Reproducibility means that the same inputs and calculation basis produce the same reported amounts. Keep the tested version with the evidence. A changed input or rate is a new comparison, not a reason to silently rewrite the original expected result.

    REPLAY THE SAME CASE

    • Same inputs + Same calculation basis
    • → Same expected amounts
    • Changed input → Separate version or case
    • Preserve the original evidence

    Part 3 of 3

    Keep diagnostic events separate from financial records. Opening a preview, making a retry, or producing an error message does not by itself prove that a new billable expense occurred. Use diagnostic evidence to investigate behavior, and financial evidence to reconcile charges.

    TWO DIFFERENT RECORD TYPES

    • Financial record | Supports a cost or allocation
    • Diagnostic log | Describes system activity
    • Preview event ≠ posted charge
    • Retry event ≠ proof of new billable usage
    • Both can support an investigation; they are not interchangeable

    OUR REVIEW PROCESS

    Report, Classify, Correct, and Recheck

    Part 1 of 3

    A useful finding lets another person repeat the check. Record the example and version, the input change, the steps, the expected result, the actual result, and the impact. A result not yet observed stays Not tested. A requirement question should say what decision is missing.

    A REPRODUCIBLE FINDING

    • Example and version
    • Input change and steps
    • Expected result
    • Actual result and outcome
    • Impact and evidence
    • Undecided requirement | Name the decision needed

    Part 2 of 3

    I will separate defects from missing data, undecided requirements, and later improvements. A missing DMS rate is an evidence gap, not automatically a software defect. Use Passed, Failed, Blocked, or Not tested for execution. Keep those separate from the workbook's review statuses.

    CLASSIFY BEFORE FIXING

    • Defect | Observed mismatch against a defined expectation
    • Data gap | Required evidence is missing
    • Requirement question | Expected behavior is undecided
    • Later improvement | Outside the agreed correction
    • Execution: Passed / Failed / Blocked / Not tested
    • Review: Reviewed / Question open / Change proposed

    Part 3 of 3

    After a correction, the original reviewer repeats the original check and one related case. Preserve the earlier result and identify the corrected version. A recheck becomes Passed only when it has been executed and supported. Our internal review does not approve DMS's commercial policies.

    CORRECTION AND RECHECK

    • Finding → Investigation → Agreed correction
    • → Original check + Related case
    • Preserve old result; identify new version
    • Reviewer evidence required
    • DMS business acceptance remains separate
